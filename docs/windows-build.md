# Сборка и установка Windows-приложения

## Выбранный путь

Windows-сборка выполняется в GitHub Actions на Windows runner. Пользователю поставляется установщик `.exe`; на его компьютере не нужны Python, Node.js или Git.

Предлагаемая цепочка:

1. CI устанавливает зафиксированную версию Node.js для production-сборки React SPA.
2. CI устанавливает зафиксированный Python и зависимости backend из lock-файла.
3. Frontend собирается в статические файлы, которые включаются в приложение.
4. PyInstaller собирает Python-приложение, FastAPI, pywebview bootstrap и статические ресурсы в Windows-пакет. Для надёжного обнаружения ресурсов предпочтителен режим `onedir`; он упаковывает runtime рядом с exe и упрощает диагностику/обновление.
5. Inno Setup формирует установщик `.exe` из проверенного пакета.
6. CI сохраняет установщик как workflow artifact. Публикация релиза — отдельное решение и не автоматизируется на ранних этапах.

`PyInstaller --onefile` может быть рассмотрен только после проверки времени старта, временной распаковки и антивирусных ложных срабатываний. Для MVP `onedir` проще отлаживать и предсказуемо включать ресурсы.

## WebView2 и pywebview

pywebview использует системный Microsoft Edge WebView2 Runtime. На многих актуальных Windows-системах он уже установлен, но это нельзя считать гарантией для всех целевых машин. До релизного решения нужно выбрать один вариант: проверить runtime в установщике и предложить официальный bootstrap, включить согласованный offline/fixed runtime пакет или установить документированную минимальную версию Windows с обязательным runtime. Установка не должна незаметно скачивать компоненты.

## Надёжность workflow

- Указывать поддерживаемые Windows runner, зафиксированные версии Python/Node и зависимостей; хранить lock-файлы.
- Триггеры — pull request и защищённая ветка; реальные API-ключи и пользовательские данные workflow не нужны.
- Запускать проверки и сборку, затем проверять структуру пакета. Подписывать бинарные файлы можно отдельным этапом после решения о сертификате и бюджете; не хранить закрытый ключ в репозитории.
- Не создавать артефакт, включающий SQLite/файлы из каталога пользователя. Собирать только из исходников и обезличенных тестовых данных.
- Загружать `.exe` как временный артефакт Actions с ограниченным сроком хранения. Публиковать постоянный релиз только после отдельного согласования.
- Для воспроизводимости сохранять версии toolchain и хеши исходников/артефактов, где это поддерживается.

## Установка и пути

- Программа устанавливается в `Program Files` (или выбранную пользователем директорию), отдельно от `%LOCALAPPDATA%\OfficeAI\`.
- Backend стартует как дочерний процесс/встроенный сервис жизненного цикла приложения, слушает только loopback и завершается при закрытии окна.
- Обновление заменяет файлы программы, но оставляет базу, документы, настройки и резервные копии нетронутыми.
- Деинсталлятор по умолчанию сохраняет пользовательские данные. Удаление данных — отдельная явно подтверждаемая опция.
- Вызовы установщика не содержат Python/Node prerequisites. WebView2 Runtime — отдельная проверка и решение, описанное выше.

## Нужны решения до релиза

1. Минимальная сборка Windows 10, которую будем поддерживать.
2. Способ доставки/требование WebView2 Runtime.
3. Цифровая подпись установщика и сертификат.
4. Версионирование, каналы обновления и процедура миграций пользовательской базы.
5. Срок хранения CI-артефактов и процедура публикации релизов.
